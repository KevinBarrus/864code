# 第五轮优化方案

## 总体判断

第五轮列出的是生产级产品差距，不都是当前 v1 的缺陷。当前优先补“文档承诺与实现不一致”“无法获得真实 Token 指标”“评测不能验证代码正确性”三类高价值闭环；其余项目按已声明的单会话、无沙箱、纯文本 TUI 边界保留或进入待办，不以空壳抽象换取表面完整度。

## 实施顺序

1. 问题一、二、十四：校正文档中的运行时边界
2. 问题三、七：接入可选服务端 usage，并为 Token 估算提供校准数据
3. 问题十七、十八、十九：增加可验证代码正确性的在线任务
4. 问题十三、二十二：补充低侵入的运行配置与键盘交互
5. 其余问题：更新待办与边界说明，不在本轮实现

## 问题一、二：Turn / Step 与 Session 文档承诺（已完成）

### 评估

问题成立，但根因是架构文档超前，不是 AgentLoop 必须立刻拆出对象。当前单一 AgentLoop 的局部状态边界足够支撑单会话、单请求执行；强行加入只有一处使用的 `Turn`、`Step` 类只会搬运局部变量，不能获得可恢复的分步执行。

### 方案

- 修正 `design/architecture.md`：v1 Runtime 由 `Session + AgentLoop` 组成，Turn 是一次 `AgentLoop.run()` 的概念边界，Step 是每次模型请求的概念边界，均暂不持久化为对象
- 将模型配置归属明确为 `Settings`，权限归属明确为 `ToolManager/PermissionManager`，活动状态仅存在于当前 `ui.py + AgentLoop` 调用栈
- `Session` 文档只承诺会话标识、工作区、完整消息、压缩记录和持久化降级状态，不再承诺 Token 用量或活动 Turn 恢复
- 在 `todo/runtime/turn-step.md` 记录升级前提：需要断点续跑、并发子任务或逐 Step 审计时，再引入持久化 Turn/Step 记录

验收：架构文档与实际职责一致；面试可明确说明当前没有 Turn/Step 实体及其原因

完成记录：架构文档已将 v1 Runtime 明确为 `Session + AgentLoop`，Turn/Step 仅为未持久化的执行边界；Session 职责、JSONL 结构和持久化范围已与实际实现对齐，并记录了升级为持久化 Turn/Step 的明确触发条件

## 问题三、七：可选服务端 Token usage 与估算校准

### 评估

问题成立，优先级 P1。`actual_tokens` 已贯穿评测模型和报告，却从未赋值；本地字符估算也不能准确覆盖代码 Token。由于项目支持 OpenAI-compatible 服务，不能无条件发送某一家才支持的 `stream_options`。

### 方案

- 在 `Settings` 新增显式能力开关 `MODEL_STREAM_USAGE`，默认关闭；用户确认服务端支持时才发送 `stream_options={"include_usage": true}`
- 扩展 `ModelEvent` 为只读 `UsageEvent`，包含 prompt、completion 和 total Token；`OpenAICompatibleClient` 从带 usage 的流结束分片解析并产生该事件
- `AgentLoop` 继续只处理文本和工具事件，但向现有 `on_event` 透传 usage 事件；TUI 忽略该展示事件
- `TimedModelClient` 收集每次请求 usage。一次评测中的所有模型请求都有 total usage 时，写入 `EvaluationResult.actual_tokens`；任一请求缺失时保持 `None`，绝不混用估算值
- 报告继续区分“估算上下文 Token”和“服务端实际 Token”。服务端 usage 开启后，用两者差异作为观察项，不反向修改上下文预算

验收：关闭能力开关时请求与当前完全一致；开启且收到 usage 分片时，在线评测 JSONL 和 HTML 显示实际 Token；缺失 usage 时字段仍为 `null`

## 问题四：每条消息 fsync

### 评估与决定

这是有意的耐久性优先取舍，不是当前缺陷。Session 消息量和单用户吞吐均较小，group-commit 会引入崩溃窗口与额外队列语义。

- 保留逐条 `fsync`
- 在 `todo/session/persistence-throughput.md` 记录触发条件：实测单 turn 持久化超过 200ms 或单进程消息写入超过 50 条/秒后，再设计带最大等待时间的 group-commit

## 问题五、十五：长会话整文件加载与内存复制

### 评估与决定

这是已记录的规模边界，当前没有长会话性能数据，不提前引入索引、数据库或缓存。

- 保留 JSONL 全量恢复和列表副本，保证恢复、压缩索引和消息顺序的简单一致性
- 合并到现有 `todo/session/memory-performance.md`：达到既定 10,000 消息、200ms 或 500MiB 阈值后，先将 JSONL 读取改为逐行迭代，再评估不可变消息视图

## 问题六：多进程 Session 写入

### 评估与决定

当前 CLI/TUI 的单会话模型是单进程写入，问题不影响既定使用方式。文件锁在跨平台、崩溃恢复和 pending 日志之间需要整体设计，不能只加一个局部锁。

- 在 `todo/session/concurrent-writer.md` 明确当前 Session 不支持多进程同时写入
- 当引入后台 Agent 或多端恢复时，采用“每个 Session 单写入者”的进程内队列/服务，而不是直接让多个进程竞争 JSONL 文件锁

## 问题八、九、十：摘要格式、频率与输入预算

### 评估与决定

三项均是可观察的压缩质量问题，但已有 fallback 保证正确性。没有真实长任务数据前，不把五段标题改造成复杂结构体，也不猜测新的压缩阈值。

- 保持当前固定标题校验和累计摘要
- 在真实多轮上下文验证中记录摘要失败率、每轮压缩次数、压缩前后 Token 和摘要请求成本
- 任一指标持续异常后，再只选择一个改动：将摘要输出改为 JSON 并严格解析；不同时引入摘要缓存、动态预算或 LLM judge

## 问题十一、十二、十三：并行工具与 Turn 预算

### 评估

工具串行执行是当前安全与审批模型的有意选择；并行读工具需要处理审批、输出顺序、取消和持久化顺序，不应和预算能力一起重写。`max_tool_rounds=10` 确实应成为可配置的运行策略。

### 方案

- 在 `Settings` 新增 `AGENT_MAX_TOOL_ROUNDS`，默认 10，启动层传给 `AgentLoop` 并校验为正整数
- 不新增并行调度或 Turn 级 wall-clock/token/cost 限制
- 在 `todo/runtime/execution-budget.md` 记录后续唯一方向：先按实际 usage 增加 Turn 级总 Token/总时长观测，再决定是否增加硬上限；在此之前保持串行工具执行

验收：可通过 `.env` 调整工具轮次；未配置时行为与当前相同；工具执行顺序与审批语义不变

## 问题十四、十六：Memory 名称与余额占位

### 评估与决定

`Memory` 是当前会话历史缓存，不是长期记忆；余额查询对通用 OpenAI-compatible API 没有可靠通用协议。

- 在 `memory.py` 和架构文档明确“进程内会话历史”定位，不新增向量检索或跨会话记忆
- 保留状态栏“暂不可查询”，不为不同服务商臆造余额接口

## 问题十七、十八、十九：代码正确性在线评测

### 评估

问题成立，优先级 P1。当前三个文件替换任务证明工具链与恢复，不足以证明 Coding Agent 修改的代码能通过测试；最终回复关键词也不应作为任务成功的核心依据。

### 方案

- 在现有独立临时工作区中新增两条真实代码任务：修复一个有失败测试的函数、完成一个带测试的函数骨架
- 任务要求模型使用现有文件工具和 `run_command`；评测器在 Agent 结束后独立用 `sys.executable -m pytest -q` 运行测试，不依赖模型的文字声明
- 断言目标测试通过、测试文件未被修改、无关文件未被修改，并保留读写前置和 Session 恢复断言
- 最终回复关键词从“任务通过”条件降为报告观察字段，不再决定代码任务成功
- 保留现有三个文件任务作为工具链真实任务，HTML 报告新增“代码正确性任务”分区，两个分区不混算成功率
- 不接入 LLM-as-a-judge；测试结果比第二个模型评分更可复现

验收：模型只改测试或未让 pytest 通过时任务失败；正确实现且测试通过时任务成功；报告能独立展示代码正确性任务的通过率和失败原因

## 问题二十：小样本任务成功率门禁

### 评估与决定

不修复。任务成功率是正确性门禁，不是性能统计；一次原本成功的确定性任务变失败也应立即报告。P95 与请求数受样本量门控是因为它们天然受网络与模型波动影响。

- 在 `design/evaluation.md` 明确该差异，避免将两种门禁混为一谈

## 问题二十一、二十二、二十三：TUI 富文本、键盘滚动与工具详情

### 评估

Markdown/语法高亮和工具详情展开是产品增强，当前纯文本自然堆叠布局已稳定；键盘滚动则是低成本可用性缺口。

### 方案

- 在 `screen.py` 为非审批状态增加 `PageUp/PageDown` 绑定，调用现有 `ConversationView.scroll_by()`，每次滚动一个当前视口高度
- 保持鼠标滚动、自动跟随和审批状态方向键行为不变
- Markdown、语法高亮和工具详情展开记录至 `todo/ui/`，在确定终端渲染方案前不改对话条目模型

验收：键盘可滚动长历史；滚到底部后恢复自动跟随；审批弹窗内仍只由上下方向键选择选项

## 问题二十四：命令工具沙箱

### 评估与决定

这是当前唯一高危产品边界，但不能用命令黑名单伪造安全。逐次审批与完整命令展示是知情确认，不是隔离。

- 维持 `run_command` 的逐次确认、工作区 cwd、超时和进程组回收
- 在 `todo/tool/security/command-sandbox.md` 明确当前不具备文件、网络、CPU、内存隔离
- 真正接入时选择外部隔离运行时作为唯一方案，例如容器/沙箱进程并显式配置可写目录、网络和资源配额；不在 Python 层实现 allowlist/denylist

## 第五轮总体验收标准

- 架构、Memory 与评测文档不再承诺 v1 未实现的运行时状态
- 支持服务端时能够展示真实 Token usage，缺失时不伪造数据
- 在线评测至少有两条以独立 pytest 结果判断的代码正确性任务
- 工具轮次可配置，键盘可浏览长对话历史
- 所有明确推迟项均有边界、触发条件与后续唯一方向
