# 方案 1：可靠性闭环与评测校准

## 目标

在不重写现有 TUI 和 AgentLoop 的前提下，先修复“运行结果、Session 文件、模型上下文”三者不一致的问题，再补齐工具边界和评测可信度。每一步都保持单一职责，并配套最小测试。

## 实施顺序

### 第一步：明确本轮消息边界

- 让 `AgentLoop` 在返回结果时单独携带本轮生成的消息序列
- 该序列包含 assistant 工具调用、tool 结果、最终 assistant 回复，以及取消或模型异常时已经产生的结构化消息
- `ui.py` 只负责把这组本轮消息交给 `Session`
- 删除通过完整消息数量切片推断增量的逻辑
- 增加“发生压缩后仍能恢复本轮完整工具链”的测试

验收：上下文压缩前后，Session 都能保存本轮所有新增消息，消息顺序与 AgentLoop 事件顺序一致

### 第二步：让 Session 持久化可恢复

- 保留当前 JSONL 主文件作为顺序日志
- 为最终写入失败的消息增加同目录 pending 日志
- Session 启动时先恢复 pending，再继续读取主日志
- 每条主日志追加后刷新文件；暂不引入数据库和复杂事务层
- 读取时允许忽略最后一条不完整尾行，并对中间损坏行继续报错
- 只有消息成功写入主日志后才追加压缩记录

验收：模拟写入失败、进程重新创建 Session 后，pending 消息可以恢复；模拟尾部半行后，历史消息仍可读取

### 第三步：收紧上下文预算与工具输出

- 将系统提示词、工具定义和消息协议开销纳入统一估算
- fallback 生成后必须再次校验预算
- 对单条超大消息采用固定硬上限和明确截断标记
- 给文件读取、文件搜索和命令执行复用统一的输出限制函数
- 命令工具增加超时；取消时清理进程组

验收：摘要失败、单条消息过大、工具输出过大时，发送给模型的上下文都不超过配置预算；工具不会无限等待或无限增长输出

### 第四步：补齐 MCP 路由和权限边界

- 工具注册键改为 `(provider_id, tool_name)`，同时保留模型可见的唯一名称
- `ToolDefinition` 保存 provider 身份，执行时由注册表查找对应绑定
- MCP 工具从 Provider 元数据读取权限和幂等性，不再统一写死
- 未注册、来源不匹配或权限信息缺失的工具拒绝执行，并返回模型可理解的工具错误

验收：两个 MCP Provider 可以提供同名工具且能正确路由；只读 MCP 工具不会被错误标记为写工具

### 第五步：修正评测入口和指标解释

- 将根目录 `evaluation` 纳入标准 `pytest` 入口
- 新增 Session 重启、压缩后恢复、取消后工具链恢复场景
- 在线评测结果保留错误类别、失败阶段、请求次数和异常信息
- baseline 比较任务成功率、P95 延迟、模型请求次数和压缩次数
- baseline 记录模型名、配置标识和评测场景版本
- 报告明确区分“模块回归”“真实在线任务”“环境或框架错误”

验收：标准 `uv run pytest` 能收集全部测试；评测报告能区分 Agent 失败和环境失败；性能指标变化能够触发 baseline 回归

## 总体验收标准

- 压缩、取消、工具失败和持久化失败不会静默丢失本轮消息
- Session 在尾部写入中断后仍可恢复可用历史
- fallback 和工具输出都有明确硬上限
- MCP Provider 路由不依赖 `if/elif`，权限信息来自工具定义
- 评测结果能说明“链路是否跑通”和“真实任务是否完成”，不混用两个结论
- 每一步新增单元测试，并通过完整测试集

## 明确延后

暂不实现向量检索、长期记忆、复杂事务数据库、完整操作系统沙箱、自动事实审查和多工具并发调度。这些能力只有在当前闭环稳定且有真实指标证明需要时再单独建问题记录。
