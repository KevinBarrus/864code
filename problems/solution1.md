# 第一轮优化方案

## 总体目标

在不重写现有 TUI 和 AgentLoop 的前提下，先修复“运行结果、Session 文件、模型上下文”三者不一致的问题，再补齐工具边界和评测可信度。每个问题独立实现、独立测试，完成后重新评估并进入下一轮问题记录。

## 问题 1 方案：明确本轮消息边界（已完成）

- 让 `AgentLoop` 在返回结果时单独携带本轮生成的消息序列
- 该序列包含 assistant 工具调用、tool 结果、最终 assistant 回复，以及取消或模型异常时已经产生的结构化消息
- `ui.py` 只负责把这组本轮消息交给 `Session`
- 删除通过完整消息数量切片推断增量的逻辑
- 增加发生压缩后仍能恢复本轮完整工具链的测试

验收：上下文压缩前后，Session 都能保存本轮所有新增消息，消息顺序与 AgentLoop 事件顺序一致

完成记录：`AgentRunResult` 已明确返回 `new_messages`，UI 已改为直接持久化本轮新增消息，相关测试通过（5 passed）

## 问题 2 方案：让 Session 持久化可恢复（已完成）

- 保留当前 JSONL 主文件作为顺序日志
- 为最终写入失败的消息增加同目录 pending 日志
- Session 启动时先恢复 pending，再继续读取主日志
- 每条主日志追加后刷新文件，暂不引入数据库和复杂事务层
- 只有消息成功写入主日志后才追加压缩记录

验收：模拟写入失败、重新创建 Session 后，pending 消息可以恢复

完成记录：新增 Session 专属 pending JSONL，持久化失败消息会落盘，`Session.restore` 会尝试迁移并恢复 pending 消息，相关测试通过（32 passed）

## 问题 3 方案：处理 JSONL 尾部损坏（已完成）

- 读取时允许忽略最后一条不完整尾行
- 中间行损坏继续抛出明确的格式错误
- 保留有效历史，不因最后一次写入中断而使整个 Session 不可用
- 增加半行、空行和中间损坏行测试

验收：尾部半行不会阻止历史恢复，中间损坏仍能被发现

完成记录：`SessionStore` 已统一处理 JSONL 读取，最后一条未完成记录会被忽略，中间或完整非法记录仍会报错，相关测试通过（32 passed）

## 问题 4 方案：为上下文 fallback 增加硬预算（已完成）

- 将系统提示词、工具定义和消息协议开销纳入统一估算
- fallback 生成后必须再次校验预算
- 对单条超大消息采用固定硬上限和明确截断标记
- 无法再裁剪时返回可解释的上下文错误

验收：摘要失败、单条消息过大时，发送给模型的上下文不超过配置预算

完成记录：fallback 已在保留最近消息后进行最终预算校验，超预算时按优先级移除旧轮次并裁剪消息，相关测试通过（30 passed）

## 问题 5 方案：限制工具输出

- 给文件读取、文件搜索和命令执行复用统一的输出限制函数
- 限制最大字节数和最大行数
- 超限时保留明确的截断标记
- 不在这一轮引入分页系统或复杂结果存储

验收：大文件、搜索结果和命令输出不会无限进入模型上下文

## 问题 6 方案：增加命令工具运行边界

- 增加命令执行超时
- 限制标准输出和错误输出大小
- 取消时清理进程组，避免子进程残留
- CPU、内存和网络沙箱暂不纳入第一轮

验收：命令超时、取消和大输出场景都能返回可理解的工具错误

## 问题 7 方案：补齐 MCP Provider 路由与权限

- 工具注册键改为 `(provider_id, tool_name)`
- `ToolDefinition` 保存 Provider 身份，执行时由注册表查找对应绑定
- MCP 工具从 Provider 元数据读取权限和幂等性
- 未注册、来源不匹配或权限信息缺失的工具拒绝执行

验收：两个 MCP Provider 可以提供同名工具且能正确路由，只读 MCP 工具不会被错误标记为写工具

## 问题 8 方案：完善取消时的工具链持久化

- 取消时保存已经产生的 assistant tool call
- 保存已经返回的 tool result
- 保存部分 assistant 文本及取消状态
- 恢复后保持原始消息顺序

验收：取消后重新 `Session.restore`，能够恢复部分回复和已经发生的工具调用链

## 问题 9 方案：区分回归测试和真实能力评测

- 将现有离线场景标记为核心链路回归
- 增加 Session 重启、压缩后恢复和取消后恢复场景
- 保留真实在线任务评测，并单独展示其结果
- 报告区分 Agent 失败、工具失败、模型失败、环境失败和评测框架失败

验收：报告不会把模块链路通过直接表述为 Agent 任务能力通过

## 问题 10 方案：让 baseline 比较真实回归指标

- 比较任务成功率、P95 延迟、模型请求次数和压缩次数
- 记录模型名、配置标识和评测场景版本
- 为指标设置明确的回归阈值

验收：性能指标恶化超过阈值时，baseline 检查失败

## 问题 11 方案：保留在线评测错误上下文

- 记录错误类别、失败阶段和原始异常文本
- 保留已完成的模型请求数、工具调用数和事件轨迹
- 在报告中区分配置、网络、模型、工具和运行器错误

验收：在线评测失败后可以定位失败阶段，不再统一显示为 `runner-error`

## 问题 12 方案：修正标准测试入口

- 让根目录 `evaluation` 被标准测试命令发现
- 运行不带额外 `PYTHONPATH` 的 `uv run pytest`
- 保留现有测试路径和模块边界

验收：干净环境下标准测试命令能够收集并通过全部测试

## 第一轮总体验收标准

- 压缩、取消、工具失败和持久化失败不会静默丢失本轮消息
- Session 在尾部写入中断后仍可恢复有效历史
- fallback 和工具输出都有明确硬上限
- MCP Provider 路由不依赖 `if/elif`，权限信息来自工具定义
- 评测结果能区分链路回归与真实任务完成
- 每个问题都有对应测试，并通过完整测试集

## 明确延后

暂不实现向量检索、长期记忆、复杂事务数据库、完整操作系统沙箱、自动事实审查和多工具并发调度。这些能力只有在第一轮完成并重新评估后，确认存在真实需求时再建立下一轮问题记录。
