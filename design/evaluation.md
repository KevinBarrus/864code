# 评测方案

## 一、目标与原则

评测服务于两个目标：

1. 发现代码回归，证明 Agent Harness 的链路正确
2. 通过真实模型重复运行，获得可以解释的行为指标

采用一套分层方案：

```text
离线契约评测 → 在线行为评测 → baseline 回归比较 → 静态报告
```

借鉴 Pi 的部分：

- 使用隔离临时工作区
- 保存完整模型和工具轨迹
- 在线任务重复运行
- 确定性断言与模型质量评分分离

借鉴 Codex 的部分：

- 将能力拆成明确的检查项
- 保存历史 baseline
- 只阻断新增失败，不把历史已知失败伪装成新回归

实现约束：

- 评测代码放在顶层 `evaluation/`
- 不反向修改 `src/core` 的生产接口
- 第一版只使用 Python 标准库和现有依赖
- 原始结果使用 JSONL，报告使用静态 HTML
- 在线评测必须显式确认，避免意外产生模型费用

## 二、评测分层

### 1. 离线契约评测

离线评测不访问网络，使用 Fake Model、Fake ToolHandler、临时工作区和故障注入，验证系统契约：

- 多轮消息是否正确传递
- 工具调用名称和参数是否正确
- 工具失败是否返回模型并继续循环
- 模型网络错误是否有限重试
- 上下文压缩和 Session 恢复是否一致
- JSONL 写入失败是否重试、降级并保留 pending 状态
- 权限拒绝、敏感信息隐藏和取消状态是否符合预期

离线场景的成功由确定性断言决定，不用于评价真实模型能力

第一版固定五类场景：

1. 多轮记忆
2. 文件读取与修改
3. 工具失败恢复
4. 上下文压缩与 Session 恢复
5. 模型网络错误重试

### 2. 在线行为评测

在线评测使用真实模型、真实工具和独立临时工作区，第一版只保留一个主链路任务：

```text
读取文件 → 修改文件 → 持久化 Session → 恢复 Session → 验证结果
```

同一任务默认重复运行 6 次。每次运行必须：

- 创建新的临时工作区
- 创建新的 Session
- 使用相同输入和工具配置
- 保存完整轨迹和最终文件状态
- 记录失败原因，不因单次失败提前停止整个评测集

后续再增加上下文压缩专项任务和网络异常专项任务

## 三、统一评测轨迹

每次运行除了保存汇总结果，还保存一份结构化轨迹：

```json
{
  "run_id": "uuid",
  "scenario": "online_main_smoke",
  "repetition": 3,
  "events": [
    {"type": "user_message", "content": "..."},
    {"type": "assistant_message", "content": "..."},
    {"type": "tool_call", "name": "read_file", "arguments": {}},
    {"type": "tool_result", "name": "read_file", "is_error": false},
    {"type": "assistant_message", "content": "..."}
  ],
  "artifacts": {
    "session_id": "uuid",
    "workspace_snapshot": "..."
  }
}
```

轨迹记录只属于评测层，不让 AgentLoop 为评测增加专用分支。评测通过 `on_event`、客户端包装器和场景执行器收集轨迹

## 四、断言与评分

### 1. 确定性断言

确定性断言负责判断事实：

- 文件内容是否正确
- 是否调用了预期工具
- 工具参数是否正确
- 工具失败后是否继续
- Session 是否可以恢复
- 是否出现持久化降级
- 是否违反权限或泄露敏感信息

确定性断言失败时，该次运行标记为失败

### 2. 模型质量评分

模型评分只作为补充，不替代确定性断言。第一版只保留可选接口，不强制增加第二次模型调用

后续接入评分模型时，评分输入必须是：

- 用户任务
- 最终文件状态
- 工具轨迹
- 最终 assistant 回复

评分结果单独保存为 `judge_score`，不能覆盖 `passed` 字段

## 五、结果与指标

每次场景运行生成一条 `EvaluationResult`，每次重复运行生成一条独立记录：

```json
{
  "run_id": "uuid",
  "scenario": "online_main_smoke",
  "repetition": 3,
  "passed": true,
  "duration_ms": 4210.4,
  "model_requests": 3,
  "tool_calls": 2,
  "tool_failures": 0,
  "retries": 0,
  "compactions": 0,
  "estimated_tokens": 1200,
  "actual_tokens": null,
  "persistence_degraded": false,
  "judge_score": null,
  "assertions": []
}
```

核心指标：

```text
任务完成率 = 通过运行数 / 运行总数
断言通过率 = 通过断言数 / 断言总数
工具成功率 = 成功工具调用数 / 工具调用总数
工具恢复率 = 工具失败后最终完成的运行数 / 发生工具错误的运行数
持久化成功率 = 未降级运行数 / 运行总数
```

性能指标：

- 平均、P50、P95 总耗时
- 平均、P50、P95 单次模型请求耗时
- 平均模型请求次数
- 平均工具调用次数
- 平均重试次数
- 平均上下文压缩次数
- 平均估算 Token
- 服务端提供 usage 时记录实际 Token

规则：

- 计数指标保留整数
- 比例指标使用百分比
- 延迟指标至少保留两位小数，并提供 P50/P95
- 实际 Token 不可用时必须明确标记为 `null`，不能用估算值冒充
- 样本量小于 5 时只展示观察值，不宣称统计稳定性

## 六、baseline 与回归门禁

每次在线评测集生成一个带版本和时间的 baseline：

```json
{
  "schema_version": 1,
  "scenario": "online_main_smoke",
  "sample_count": 6,
  "pass_rate": 0.8333,
  "p50_duration_ms": 3900.2,
  "p95_duration_ms": 6200.8
}
```

回归比较采用以下规则：

1. 场景、输入和重复编号必须能一一对应
2. 新增失败属于回归，报告中标红
3. 历史已知失败继续单独记录，不重复计为新增回归
4. 缺失运行、重复运行和评测器异常都单独报告
5. 性能和 Token 只做趋势比较，不因为网络波动直接阻断开发

第一版不做复杂统计显著性检验，只报告样本数、均值、P50、P95 和与 baseline 的差值

任务成功率是正确性门禁，不检查样本量——一次原本成功的确定性任务变失败也会立即报告回归；P95 耗时和平均请求数受样本量门控（样本少于 20 时不比较），因为它们天然受网络和模型波动影响。两种门禁的样本量策略不同是有意设计，不混为一谈

## 七、报告

报告生成流程：

```text
运行轨迹 JSONL + 结果 JSONL + baseline
                    ↓
              静态 HTML 报告
```

报告至少展示：

- 离线五类场景通过情况
- 在线重复运行的样本数和通过率
- 每次运行的状态和失败原因
- 工具成功率和工具恢复率
- Session 持久化成功率
- 平均、P50、P95 耗时
- Token 类型和 Token 数量
- 当前结果与 baseline 的差值
- 新增失败、历史已知失败和缺失样本

不引入数据库、查询服务或前端框架，HTML 可以直接打开用于调试和面试展示

## 八、实现顺序

已完成：

1. 评测场景、断言和结果数据结构
2. Fake Model、Fake ToolHandler
3. 五类离线场景
4. 指标计算和结果 JSONL
5. 静态 HTML 报告
6. 一次在线主链路冒烟入口

已完成：

7. 为评测结果增加 `run_id`、`repetition` 和完整事件轨迹
8. 将在线主链路改为默认重复 6 次
9. 增加平均值、P50、P95 和样本量展示
10. 增加 baseline 文件和新增失败回归比较
11. 运行 6 次真实在线评测，保存结果和报告
12. 增加并验证真实上下文压缩和网络异常专项评测
13. 运行全量测试，核对离线结果、在线结果和 baseline 报告

## 九、验收标准

- 离线评测不访问网络且可以重复运行
- 五类离线场景均有可执行断言
- 故障注入不修改生产代码
- 在线评测使用独立临时工作区
- 在线主链路默认重复 6 次
- 每次运行保存完整模型和工具轨迹
- 结果 JSONL 保存 `run_id`、重复编号、统计指标和断言
- 报告展示样本量、通过率、平均值、P50 和 P95
- 报告明确区分估算 Token 和实际 Token
- baseline 可以识别新增失败、缺失运行和重复运行
- 至少完成一轮 6 次真实模型在线评测
- 评测结果可以用于解释 Agent Harness 的稳定性、恢复能力和性能变化
